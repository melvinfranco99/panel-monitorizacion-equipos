El principio que sigue la organización es la separación de responsabilidades: cada fichero hace una sola cosa. Así, si mañana quiero cambiar SQLite por PostgreSQL, solo toco db.py.

config.py — la configuración

Lee los valores de variables de entorno (el fichero .env se carga con python-dotenv). Así las contraseñas no están escritas en el código ni se suben a GitHub (.env está en .gitignore). Es una práctica de la metodología Twelve-Factor App.

INTERVALO = int(os.environ.get("MONITOR_INTERVALO", "30"))
FALLOS_PARA_CAIDO = int(os.environ.get("MONITOR_FALLOS_PARA_CAIDO", "2"))

db.py — la base de datos

Tres tablas:

TablaUna fila es…Campos clave
equiposun equipo vigilado, con su estado actualid, nombre, ip (UNIQUE), tipo, puerto, estado, latencia_ms, fallos_consecutivos
comprobacionesuna comprobación (el historial)equipo_id (FK), fecha, responde (0/1), latencia_ms
eventosun cambio de estado (incidencia)equipo_id (FK), fecha, estado_anterior, estado_nuevo

Relación 1 a N: un equipo tiene muchas comprobaciones y muchos eventos. ON DELETE CASCADE hace que al borrar un equipo se borre su historial. Hay un índice en (equipo_id, fecha) porque casi todas las consultas filtran por esas dos columnas; sin él, SQLite recorrería la tabla entera.

Tres detalles que conviene saber explicar:

  • row_factory = sqlite3.Row → acceder a fila["ip"] en vez de fila[2].
  • PRAGMA journal_mode = WAL → permite leer (la web) mientras se escribe (el monitor) sin bloquearse.
  • get_db() guarda la conexión en g, un objeto de Flask que vive lo que dura una petición; cerrar_db la cierra al terminar.

comprobador.py — ¿responde el equipo?

El corazón técnico. hacer_ping() ejecuta el comando ping del sistema operativo:

comando = ["ping", "-c", "1", "-W", "1", host]          # Linux
comando = ["ping", "-n", "1", "-w", "1000", host]       # Windows
resultado = subprocess.run(comando, capture_output=True, text=True, timeout=3)
  • ¿Por qué el comando y no enviar ICMP desde Python? Crear paquetes ICMP a mano necesita un raw socket, que exige permisos de root. El comando ping ya tiene esos permisos concedidos por el sistema.
  • Código de salida (returncode): 0 = respondió. En Windows hay una trampa: «Host de destino inalcanzable» también devuelve 0, por eso se comprueba que en la salida aparezca TTL=.
  • Latencia: se extrae con una expresión regular de time=12.3 ms.
  • Seguridad: se pasa una lista de argumentos y sin shell=True, y antes direccion_valida() solo acepta IPs o nombres DNS. Si alguien escribiera 1.1.1.1; rm -rf / como IP, se rechaza (hay un test que lo comprueba).

comprobar_tcp() usa socket.create_connection(): si se completa el saludo de tres pasos (SYN → SYN-ACK → ACK) el puerto está abierto y el servicio escucha.

monitor.py — el vigilante

La clase Monitor arranca un hilo (threading.Thread, daemon=True para que muera con el programa) con un bucle infinito:

while not self._parar.is_set():
    self._ciclo_seguro()
    self._parar.wait(self.config["INTERVALO"])   # espera, pero se puede interrumpir

Dentro de cada ciclo, las comprobaciones se hacen en paralelo:

with ThreadPoolExecutor(max_workers=min(64, len(equipos))) as pool:
    resultados = list(pool.map(lambda e: comprobar_equipo(e, timeout, demo), equipos))

Usar hilos aquí es correcto aunque Python tenga el GIL, porque el trabajo es de entrada/salida (esperar respuestas de la red), no de cálculo: mientras un hilo espera, los otros avanzan.

La regla de estado está en una función pura (sin base de datos ni red), así se puede probar fácilmente:

def calcular_estado(estado_actual, fallos_consecutivos, responde, fallos_para_caido):
    if responde:
        return "up", 0
    fallos = fallos_consecutivos + 1
    if fallos >= fallos_para_caido:
        return "down", fallos
    return estado_actual, fallos

Es una pequeña máquina de estados: desconocido → up ⇄ down. Exigir 2 fallos seguidos evita falsas alarmas por un paquete perdido (en Wi-Fi pasa a menudo).

Un threading.Lock impide que se ejecuten dos ciclos a la vez (por ejemplo, el automático y el del botón «Comprobar ahora»).

estadisticas.py — la disponibilidad

La disponibilidad es simplemente:

disponibilidad = comprobaciones con respuesta ÷ comprobaciones totales × 100

Como responde vale 0 o 1, la media es directamente ese porcentaje, y SQL lo calcula en una línea:

SELECT AVG(responde) * 100 FROM comprobaciones WHERE equipo_id = ? AND fecha >= ?

Para las barras se agrupa el historial en tramos (1 hora para 24 h, 6 horas para 7 días, 1 día para 30 días).

Dato para la defensa — los «nueves»: 99 % de disponibilidad son 7,2 h caído al mes; 99,9 % son 43 min; 99,99 % son 4,3 min. Los contratos de servicio (SLA) se expresan así.

seguridad.py — login y CSRF

  • Contraseña con hash: generate_password_hash (Werkzeug, algoritmo scrypt con sal). Se compara con check_password_hash. Nunca se compara texto plano.
  • Sesión: Flask guarda session["admin"] = True en una cookie firmada con SECRET_KEY; el usuario puede leerla pero no falsificarla.
  • CSRF: cada formulario lleva un token aleatorio guardado en la sesión. Antes de cada POST se comprueba. Así otra web no puede hacer que tu navegador borre equipos sin que lo sepas.
  • Decoradores @login_requerido y @lectura_permitida: envuelven una función para añadir la comprobación sin repetir código.
  • hmac.compare_digest compara en tiempo constante (evita ataques de temporización).

Borrar usa POST y no GET a propósito: GET no debe cambiar nada (un buscador o un precargador de enlaces podría «visitar» un enlace de borrado).

Las consultas usan parámetros (? o :nombre): los datos nunca se pegan al texto SQL, así que no hay inyección SQL.

Tras guardar se hace redirect (patrón Post/Redirect/Get) para que al recargar la página no se reenvíe el formulario.

__init__.py — create_app()

Patrón application factory: una función que crea y devuelve la app. Ventaja: los tests pueden crear apps con otra configuración (base de datos temporal, sin monitor) sin tocar la real.

app = Flask(__name__)
app.config.from_object(Config)      # 1. configuración
db.inicializar(...)                 # 2. tablas
seguridad.preparar(app)             # 3. CSRF y login
app.register_blueprint(web)         # 4. rutas
Monitor(app.config).iniciar()       # 5. hilo vigilante

Plantillas y JavaScript

base.html tiene la cabecera y el pie; las demás páginas la heredan con {% extends "base.html" %} y rellenan el bloque contenido. Jinja2 escapa automáticamente {{ variable }}, lo que evita XSS.

La página principal se actualiza sola con AJAX: app.js llama cada 5 s a fetch("/api/estado"), recibe JSON y redibuja las tarjetas sin recargar la página. Como aquí el HTML se construye en JavaScript, se usa la función esc() para escapar los textos.

La gráfica de latencia se dibuja a mano en SVG (sin Chart.js) para que el panel funcione en una red de empresa sin acceso a Internet.

El CSS usa variables (--ok, --mal…) y prefers-color-scheme para el modo oscuro automático, y grid con auto-fill para que las tarjetas se adapten al móvil (diseño responsive).

Tests automáticos

pip install -r requirements-dev.txt
python -m pytest -v

22 pruebas con pytest: validación de IPs (incluidas maliciosas), regla de estado, ping real a 127.0.0.1, puerto TCP cerrado, registro de eventos, API, alta/edición/baja, que no se pueda añadir sin login y login incorrecto. Haz una captura de la salida para los anexos de la memoria.

Recorrido de una petición completa

Qué pasa cuando abres el panel, de principio a fin (muy útil para contar en la defensa):

  1. El navegador pide GET /. Flask busca qué función tiene esa ruta: inicio().
  2. @lectura_permitida comprueba si hace falta login.
  3. render_template("inicio.html") devuelve el HTML base; el navegador pide también estilo.css y app.js.
  4. app.js ejecuta fetch("/api/estado"). Flask ejecuta api_estado(), que consulta SQLite y responde JSON.
  5. El JavaScript dibuja las tarjetas. A los 5 s repite el paso 4.
  6. Mientras tanto, en paralelo, el hilo monitor sigue haciendo pings y escribiendo en SQLite. La próxima vez que el navegador pregunte, verá los datos nuevos.
