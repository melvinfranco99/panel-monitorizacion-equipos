Instalar y usar NetPanel

Desde probarlo en tu portátil en cinco minutos hasta dejarlo funcionando en un servidor de empresa con HTTPS.

1. Instalación básica

Necesitas Python 3.10 o superior y Git.

git clone https://github.com/melvinfranco99/panel-monitorizacion-equipos.git
cd panel-monitorizacion-equipos
python3 -m venv .venv              # entorno virtual: las librerías quedan dentro del proyecto
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env               # y edita la contraseña
python run.py                      # abre http://localhost:5000

La primera vez Windows preguntará si permites a Python usar la red: acepta en redes privadas.

2. Primer uso

  1. Abre http://localhost:5000. Al principio no hay equipos.
  2. Pulsa Entrar e inicia sesión con el usuario y contraseña del fichero .env (por defecto admin / admin, y el panel te avisará en rojo de que la cambies).
  3. Pulsa + Añadir: nombre, IP, tipo y, si quieres, un puerto TCP.
  4. O importa muchos de golpe desde un CSV: 
    python herramientas.py importar ejemplos/equipos_casa.csv
  5. Para comprobar desde la terminal sin abrir la web: 
    python herramientas.py comprobar

Formato del CSV (la primera línea son los nombres de columna):

nombre,ip,tipo,puerto,ubicacion,descripcion
Router de casa,192.168.1.1,router,,Salón,
Servidor web,192.168.1.11,servidor,80,Rack,Comprueba el puerto 80

Tipos válidos: router, switch, servidor, ordenador, impresora, otro.

3. Tres entornos de uso

Un entorno controlado es una red de pruebas donde tú decides qué falla y cuándo. Sirve para demostrar que la aplicación funciona sin tocar una red real. Tienes tres opciones, de más fácil a más realista:

Opción A · Modo demo (sin red)

Los resultados se simulan. Ideal para la presentación si en el aula no hay red o bloquea el ping.

# Linux / macOS
MONITOR_MODO_DEMO=1 python herramientas.py demo     # 12 equipos de ejemplo + 7 días de historial
MONITOR_MODO_DEMO=1 python run.py

# Windows (PowerShell)
$env:MONITOR_MODO_DEMO=1; python herramientas.py demo; python run.py

Sale una franja amarilla avisando de que es una simulación: sé transparente con el tribunal.

Opción B · Red Docker (recomendada para demostrar)

La carpeta lab/ crea una red privada 172.30.0.0/24 con un «router», un servidor web nginx, un servidor de ficheros, dos PCs y una impresora, todos como contenedores, y el panel vigilándolos.

cd lab
docker compose up -d --build          # abre http://localhost:5000  (admin / laboratorio)

docker compose stop pc-contabilidad   # «desenchufar» un PC: en ~20 s sale CAÍDO
docker compose start pc-contabilidad  # vuelve a RESPONDE y queda registrado en Incidencias
docker compose stop servidor-web      # el servidor web (comprobado por TCP 80) cae

docker compose down -v                # borrarlo todo al acabar

Si docker compose no existe, instala el plugin: en Arch sudo pacman -S docker-compose; en Debian/Ubuntu sudo apt install docker-compose-plugin; en Windows viene con Docker Desktop.

Grabar este experimento (apagar, ver la caída, encender, ver la recuperación) con capturas o vídeo es una evidencia perfecta para la memoria y la defensa.

Opción C · Máquinas virtuales

Con VirtualBox: crea 2 o 3 VMs (un Debian, un Windows, un pfSense como router) en una «Red interna» o «Solo anfitrión», dales IP fija y añádelas al panel. Apaga una VM o activa su cortafuegos para ver la diferencia entre ping y TCP. Es lo más parecido a una red real y permite enseñar el caso de Windows bloqueando ICMP.

  1. Averigua tu red. En Linux ip route (la IP tras default via es tu router); en Windows ipconfig («Puerta de enlace predeterminada»).
  2. Inventaria tus equipos. Entra en la web del router (normalmente esa IP) → lista de clientes DHCP. Ahí verás IP y nombre de cada dispositivo.
  3. Fija las IPs. En el router, crea reservas DHCP para los equipos que quieras vigilar: así su IP no cambia. Si no, mañana el NAS puede tener otra IP y saldrá «caído» sin estarlo.
  4. Carga los equipos copiando ejemplos/equipos_casa.csv y cambiando las IPs. Incluye 8.8.8.8 para saber si «se ha caído Internet» o solo tu red.
  5. Déjalo encendido. En un equipo que siempre esté encendido: una Raspberry Pi es ideal (consume ~3 W). Instálalo como servicio: 
    sudo bash deploy/instalar_linux.sh
    El servicio escucha solo en 127.0.0.1; para verlo desde el móvil en casa cambia en /etc/systemd/system/netpanel.service -b 127.0.0.1:5000 por -b 0.0.0.0:5000 y entra a http://IP-de-la-raspberry:5000.
  6. Avisos al móvil con Telegram (ver sección 5).

No abras el puerto 5000 en el router hacia Internet. Si quieres verlo desde fuera de casa, usa una VPN (WireGuard, Tailscale) en lugar de exponer el panel.

En una empresa cambian tres cosas: permisos, seguridad y fiabilidad.

Antes de instalar

  • Autorización por escrito del responsable de sistemas. Vigilar equipos ajenos sin permiso puede ser una falta o algo peor.
  • Pedir el inventario (o la hoja de direccionamiento IP) y decidir qué es crítico: router, cortafuegos, servidores, controlador de dominio, NAS, impresoras.
  • Reglas de cortafuegos: permitir ICMP echo y los puertos TCP necesarios solo desde la IP del servidor de monitorización. En Windows: regla de entrada «Archivo e impresora compartidos (petición de eco ICMPv4)», que se puede desplegar por GPO a todos los equipos.
  • Si hay VLANs, colocar el servidor en la VLAN de administración con rutas hacia las demás.

Instalación de producción

  1. Una VM Debian/Ubuntu Server pequeña (1 vCPU, 1 GB RAM) en el hipervisor de la empresa (Proxmox, VMware, Hyper-V).
  2. sudo bash deploy/instalar_linux.sh: crea un usuario sin privilegios netpanel, el entorno virtual, genera clave secreta y contraseña aleatorias y registra el servicio systemd.
  3. Instala nginx como proxy inverso con HTTPS: plantilla en deploy/nginx-netpanel.conf. Limita con allow/deny qué red puede ver el panel.
  4. En /opt/netpanel/.env pon MONITOR_LOGIN_LECTURA=1 para que haga falta usuario incluso para mirar.
  5. Crea un nombre DNS interno (p. ej. netpanel.empresa.local) en el servidor DNS / controlador de dominio.
  6. Importa el inventario con herramientas.py importar inventario.csv.
  7. Copia de seguridad del fichero instance/monitor.db (basta con un cron diario con sqlite3 monitor.db ".backup copia.db").
  8. ¿Quién vigila al vigilante? Conviene comprobar desde fuera que el panel está vivo (otro NetPanel o un servicio externo).

Arquitectura recomendada:

[Usuarios IT] --HTTPS--> nginx (443) --> gunicorn 127.0.0.1:5000 --> NetPanel
                                                          |
                                     ICMP/TCP --> routers, servidores, PCs (todas las VLAN)

Límites honestos: a partir de varios cientos de equipos, o si se necesitan métricas de CPU, disco o tráfico (SNMP, agentes), lo profesional es Zabbix, LibreNMS o PRTG. NetPanel cubre la pregunta «¿está vivo?» en redes pequeñas y medianas.

4. Configuración (.env)

VariablePor defectoPara qué sirve
SECRET_KEY(de desarrollo)Firma la cookie de sesión. Cámbiala siempre.
MONITOR_ADMIN_USUARIO / _PASSWORDadmin / adminCredenciales del administrador.
MONITOR_INTERVALO30Segundos entre comprobaciones.
MONITOR_TIMEOUT1Segundos de espera máxima de cada respuesta.
MONITOR_FALLOS_PARA_CAIDO2Fallos seguidos para marcar un equipo como caído.
MONITOR_RETENCION_DIAS30Días de historial que se guardan.
MONITOR_DBinstance/monitor.dbRuta de la base de datos.
MONITOR_MODO_DEMO01 = resultados simulados.
MONITOR_LOGIN_LECTURA01 = pedir usuario también para ver el panel.
MONITOR_TELEGRAM_TOKEN / _CHAT_ID(vacío)Avisos por Telegram.

Cálculo rápido del tamaño del historial: 50 equipos × 2 comprobaciones/min × 60 × 24 × 30 días ≈ 4,3 millones de filas ≈ 200–300 MB. Si es mucho, sube el intervalo a 60 s o baja la retención.

5. Avisos por Telegram

  1. En Telegram, habla con @BotFather → /newbot. Te da un token.
  2. Escribe cualquier cosa a tu bot y abre https://api.telegram.org/bot<TOKEN>/getUpdates: el número en "chat":{"id":…} es tu chat_id.
  3. Ponlos en .env (MONITOR_TELEGRAM_TOKEN y MONITOR_TELEGRAM_CHAT_ID) y reinicia. Recibirás «🔴 CAÍDO: …» y «🟢 RECUPERADO: …».

6. Problemas típicos

Un PC con Windows sale siempre caído, pero funciona

El cortafuegos de Windows bloquea el ping por defecto. Opciones: activar la regla «petición de eco ICMPv4» o, mejor, indicar un puerto TCP que tenga abierto (3389 si tiene escritorio remoto, 445 si comparte carpetas).

En Docker o Linux el ping da «Operation not permitted»

Enviar ICMP necesita un socket especial. En Linux moderno se permite a usuarios normales mediante net.ipv4.ping_group_range; en Docker el contenedor necesita la capacidad NET_RAW (activada por defecto). Si la quitaste, usa comprobaciones TCP.

Todo sale caído de golpe

Lo más probable es que el problema sea del propio servidor del panel (cable, Wi-Fi, gateway). Por eso conviene vigilar también el router y 8.8.8.8: si todo cae a la vez, el problema está cerca del monitor.

Un equipo aparece y desaparece (flapping)

Wi-Fi débil o red saturada. Sube MONITOR_FALLOS_PARA_CAIDO a 3 o MONITOR_TIMEOUT a 2.

«Token CSRF inválido»

La sesión caducó o cambiaste la SECRET_KEY. Recarga la página e inténtalo de nuevo.

Con gunicorn las comprobaciones salen duplicadas

Estás usando varios procesos (-w 4). Cada proceso arranca su propio monitor. Usa -w 1 --threads 8.

7. Uso responsable y legal

Monitoriza solo redes tuyas o en las que tengas autorización expresa. Enviar paquetes a equipos ajenos de forma sistemática puede considerarse un escaneo no autorizado. En empresa, el panel almacena IPs y nombres de equipos asociados a personas («PC de Dirección»): son datos que entran en el ámbito del RGPD/LOPDGDD, así que el acceso debe estar limitado al personal de sistemas.
